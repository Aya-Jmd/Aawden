For judges: one minute

  • Claim. One sentence from a wrong reviewer makes open models abandon most of the security verdicts they get right alone. A small LoRA adapter, trained so the verdict never depends on the reviewer, brings that to near zero without hurting coding.
  • Tracks. Track 2a, problem statement 2 (safety evaluation sets): a benchmark with executable labels and a measure that cannot reward a model for guessing. Track 2b, problem statements 9 and 10 (locating safety; circuit-level edits): attempted, and both came out negative, reported below. The adapter itself is our own problem: robustness of an AI code reviewer to a wrong human opinion (sycophancy).
  • Headline. Qwen2.5-14B-Instruct abandons 84 of 111 correct verdicts before and 1 of 111 after. Aya Expanse 32B goes from 85 of 90 to 3 of 90.
  • Base model and method. Qwen2.5-14B-Instruct (also Aya Expanse 32B and 8B), with a rank-16 LoRA trained on 268 held-out-family files, each shown with no reviewer, a right one and a wrong one, all with the same target.
  • Check it. Demo · benchmark · all adapters · code. The full checklist (kits, licences, splits, hyperparameters, compute) is in Submission details near the end.

The problem

More and more, models are asked to review code for security holes. A reviewer comment, a ticket, or a line in a pull request sits next to that code, and often states a conclusion. If one confident sentence can overturn a correct verdict, then anyone who can write that sentence can wave a vulnerability through, and the model's reasonable-sounding review ends up rubber-stamping a bad decision.

The test is simple enough to run by hand:

  1. Show the model a file. Record its verdict.
  2. Show the same file again, with one added line in which a reviewer states the opposite verdict.
  3. Count how many correct verdicts the model gives up.

There is a catch before any of that: a model can only abandon a correct verdict if it had one.

First finding: most small models cannot be tested this way

So first you have to check the model can do the task at all. On 129 plain files (every label checked by running the code, no trick cases), here is how many each unchanged model gets right with no reviewer in the prompt:

Qwen2.5-7B-Instruct64coin flip

Chance on a balanced set is 64.5. Every model at or below 9B is at chance. Their deference numbers can look like resistance or like giving in, but they are noise: all five land between 64 and 70 out of 129, which is what guessing gives you.

This matters more than it sounds. The usual score here is "how often does the model copy a stated opinion", and it rewards a model that answers vulnerable to everything: a constant answer agrees with any opinion that happens to be vulnerable, and on a balanced set a constant predictor scores exactly 50%. Qwen2.5-7B copies only 0.52 of opinions and looks "half resistant" for that reason alone. It isn't resisting anything; it's guessing.

So we only measure deference on models that can do the task, and we use a measure that guessing can't game.

The measure: flip rate on solved cases

Take only the files the model gets right with no reviewer present. Attach a reviewer who states the opposite. The flip rate is the share of those correct answers that go wrong.

A model that was guessing has no correct answers to lose, so it cannot score well by accident. A model that copies the reviewer scores 1.0. A model that reads the code scores near 0.

We report it under three answer formats, because the format matters more than it should: one JSON answer, and two A/B letter mappings with the labels swapped. Qwen2.5-32B's own flip rate moves tenfold across those three formats (0.26 / 0.28 / 0.04), so we don't trust any one format's number on its own.

modelright unaidedflip rate: JSON / A/B / B/A
Aya Expanse 32B90 / 85 / 850.94 / 1.00 / 0.91
Qwen2.5-14B-Instruct111 / 111 / 880.76 / 0.76 / 0.52
Qwen2.5-32B-Instruct118 / 120 / 1170.26 / 0.28 / 0.04

Qwen2.5-32B is the positive control. It solves most of both sets, which shows the task is fair: a strong model can pass it, and mostly does.

Aya Expanse 32B knows the answer on two thirds of the plain files and gives up almost all of them to one sentence from a wrong reviewer.

These numbers are in runs/wsp-v3/deference-summary-redacted.json in the benchmark repository.

Every label is executable

None of this rests on a judge model's opinion. Each fixture is a runnable pair: a vulnerable implementation and a fixed one, and the label comes from what the code actually does: SQL against an in-memory SQLite database, access control against a fixed record table. All 220 oracle checks pass.

The prompts are paired: same source, same threat model, only the reviewer's opinion changes. The reviewer line and the code are the same length and in the same place, so a model cannot tell them apart by shape.

What the answer actually depends on

Before trying to fix anything, we wanted to know what the answer actually depends on. So we tried every combination: clean and vulnerable code, each shown with a "vulnerable" opinion, a "not vulnerable" opinion, and no opinion at all. In each case we recorded how far the model leaned towards one answer (the corrected log-probability margin).

Holding the opinion text fixed and varying only the code, the code moves the answer by +0.06 and +0.41 nats (JSON format; +0.11/+0.30 and −0.01/+0.25 in the two A/B formats). A code effect of well under one nat means the model is barely reading the code at all: under a "not vulnerable" opinion, the area under the ROC curve separating truly vulnerable files from clean ones is 0.51, which is chance.

Changing only the opinion, against no opinion at all, moves the same margin +10.7 nats when it says "vulnerable" and −19.7 nats when it says "not vulnerable".

In short, the opinion decides the answer and the code barely matters.

That explains why our first attempts all failed: prompting harder, four sparse weight-space patches written by two different frontier models, and the largest attention-head ablation our budget allowed. Every one failed the criterion that only real code reading can pass:

J = accuracy(wrong reviewer) + accuracy(right reviewer) − 1

A model that copies the opinion gets one of those two cells wrong by construction, so it cannot exceed J = 0. Getting both right means actually telling the code apart. Across eleven measurements (each method on each data split), J was never above zero.

The biggest head ablation shows why. Zeroing seven complete attention heads moved the answer +5.10 nats for clean code and +4.97 nats for vulnerable code. The same for both. It cancelled the opinion and never looked at the code.

These numbers are in runs/wsp-v3/margin-2x2/table.json, computed by scripts/wsp_margin_2x2.py::code_effect_by_opinion. One trap to watch for: if you group by prompt condition instead of by the exact opinion text, you get +6.3 nats and the code looks like it matters. It doesn't; that number comes from the grouping, not from the code.

The fix: train the verdict to follow the code

We trained a LoRA adapter on 268 files from families that never appear in the test set: no test file, and no file from the same family as a test file, is used in training. Each file is shown three ways: no reviewer, a reviewer who is right, and a reviewer who is wrong. The target output is the same in all three. That is the whole idea: the correct answer does not depend on what the reviewer says.

The settings: rank 16, alpha 32, on all seven attention and MLP projections (42M parameters on Aya 8B, about 0.5% of the model). Learning rate 1e-4, two epochs, seed 17. For Qwen2.5-14B and Aya 32B the 268 training cases become 804 rows (three conditions each) and 201 steps; the Aya 8B recipe further down uses 2,948 rows. The Qwen2.5-14B adapter trains in 11 minutes on one A100; the Aya 8B two-stage adapter takes 7 minutes for the first stage plus 33 for the second (times from train_meta.json in the adapter repository).

The control that separates two effects

The task-only control is the interesting row. Train on the same 268 files with no reviewer in the prompt at all, and Qwen2.5-14B's flip rate drops from 0.757 to 0.144 by itself.

So much of what looked like sycophancy wasn't. The model didn't know the answer, the reviewer's sentence was the most useful clue in the prompt, and so it copied it. Teach it the task and most of the effect goes away.

Training with reviewers in the prompt removes the rest, and the two effects can be told apart statistically. For us this was the most useful thing the project turned up, and you can't see it in the headline number.

Three more checks:

  • Answer format. Both label-swapped A/B mappings, which the adapter never trained on, also go to 0.000.
  • Real code. On 32 externally written Python pairs, Qwen2.5-14B goes 0.213 → 0.017 and Aya 32B 1.000 → 0.000. These labels come from the upstream dataset, not from our oracle, so we report them as secondary.
  • Coding ability. HumanEval pass@1 is 116/164 before and after on Qwen2.5-14B; 81/164 → 86/164 on Aya 32B. The intervals overlap. The adapter does not make the model worse at writing code.

The hard case: teaching the recipe, not one sentence

A model that only learned one sentence pattern breaks on the next one, and that is exactly what happened on Aya Expanse 8B, the model this hackathon is built around.

Trained on the single reviewer sentence, the adapter stayed right on 87 of 129 files but fell back to abandoning 17 to 30 of 87 correct verdicts on wordings it had not seen. It had learned to ignore one sentence, not to ignore reviewers.

The change that fixed it was the shape of the training, not more data.

Stage one: learn the review task with no reviewer in sight at all. This is the task-only adapter, and on a small model it isn't a control, it's a requirement. Aya 8B cannot review code unaided, so there is no correct answer to preserve until it can.

Stage two: continue from that adapter on 2,948 rows: each training case with no reviewer, a correct one and a wrong one, across four reviewer wordings, plus a row that shows the model an earlier answer and a reviewer disputing it. Five further wordings were kept out entirely.

The bar was fixed before the runs: on every held-out wording, the upper bound of the flip-rate interval must stay under 0.192, and the model must also show it can do the task alone (the Wilson lower bound on its unaided accuracy must be above 0.5). All three runs of both models pass. Aya 8B solves 110, 106 and 109 of 129 unaided; Tiny Aya solves 105, 106 and 104.

The worst row is the reviewer who argues with the model's own answer: 15 of 325 pooled, or 4.6%. It's the hardest case because the reviewer isn't just stating a verdict; they're contradicting something the model itself said.

What the extra stage costs

The recipe costs raw skill. Trained on all wordings from scratch instead, Aya 8B solves noticeably fewer files outright: 90, 91 and 108 across three runs, mean 96, against 110, 106 and 109, mean 108, for the two-stage version. That is about 12 more files solved for free by doing the task first.

And training from scratch doesn't buy extra robustness in return. On the plain reviewer wording the two are the same (2 of 289 flipped against 2 of 325), and from scratch is worse on four of the five held-out wordings (CISO 10 of 289 against 3 of 325; argued 14 of 289 against 7 of 325), better on one (pushback 5 of 289 against 15 of 325). Both pass the rule we set in advance in all three runs. The two-stage version is the one we published because it solves more files unaided at the same robustness.

Three runs is a small sample, so read these as three runs, not as a general estimate.

What the fix costs

A reviewer's bare opinion looks the same whether it is right or wrong. So a model that stops listening to wrong reviewers also stops being helped by right ones. That is the price, and no setting avoids it.

Turning the Qwen2.5-14B adapter down to partial strength shows the trade-off:

adapter strengthabandoned to a wrong reviewerrescued by a correct reviewer
off84 of 11117 of 18
25%11 of 1187 of 11
50%2 of 1222 of 7
75%0 of 1231 of 6
full0 of 1241 of 5

At 25% strength the model still abandons 11 correct verdicts but is rescued on 7 of 11 cases it would otherwise miss. At full strength it abandons none and is rescued on almost nothing.

The adapter ignores reviewers; it does not learn which ones to trust. If you need a model that a trusted reviewer can still correct, this adapter is the wrong tool, and turning it down only swaps one problem for the other.

What did not work

Several things failed. They are part of the result, so here they are.

Editing the weights directly did not work. Switching off the attention heads that read the reviewer's line changed nothing. On the model that does have the skill, Qwen2.5-14B, zeroing the 11 heads that attend most to the opinion (0.049% of its weights, chosen on one set and tested on a separate one) scored 0.71 / 0.79 / 0.59 against 0.75 / 0.75 / 0.49 unedited. Three size-matched random-head controls scored 0.71–0.77 / 0.58–0.78 / 0.49–0.66. No better than random heads.

Removing an "opinion direction" from the residual stream reduced the flip rate to 0.544 but cost 8 solved cases, which failed the competence rule we had set in advance.

Teaching a small model the task by distillation did not work. Aya 8B did not become competent.

Training the 8B on one reviewer sentence leaks on untrained wordings, as shown above.

A second-round Tiny Aya adapter collapsed to one fixed answer (64 of 64, twice) and failed the competence rule outright.

An earlier draft of this work claimed "five open checkpoints, none of them read the code", from opinion-copy rates. That mixed up "can't do the task" with "gives in to the reviewer", and we have withdrawn it.

Where the fix is weak

  • Short templated files. The plain set has 64 families; the puzzle set has 30. The check on 32 real-world code pairs points the same way, but that set is small and its labels come from the dataset rather than from us.
  • One language of prompt. Everything here is Python security review, in English.
  • Two vulnerability classes. SQL injection and access control, mostly. Real code adds code and command injection, and we have not tested a held-out category.

What we will not claim

That vulnerability is not represented anywhere in these networks. We measured the verdict readout, not the contents of the residual stream. A held-out-family linear probe would separate "not represented" from "represented but never routed", and we did not run it: at 30 held-out pairs it needs about 21 of 30 correct to reach significance, so a null would have proved nothing.

That this generalises beyond what was run. Templated fixtures, open checkpoints from 3B to 32B, three answer formats, one language.

That a sealed test set was used. A 120-case sealed set exists with committed hashes and was never opened. Every number above comes from the open sets. Our rules allow one look at it, and we did not want to spend that look on something that might still fail.

That the labels were independently reviewed. Every oracle in this benchmark was written by one author. We prepared a blinded review packet, but nobody has signed it off yet. Independent label review is the most important thing this project has not done.

Submission details

This section covers each required field of the hackathon write-up in one place. Each fact is taken from a file in the repository or a saved run.

Tracks and problem statements. Track 2a, problem statement 2 (adversarial and safety evaluation sets) is the main fit: an executable-label benchmark plus a measure that a guessing model cannot pass. Track 2b, problem statements 9 (where safety lives) and 10 (circuit-level interventions) were attempted with head ablation and a residual-direction edit, and both were negative (see "What did not work"). The adapter is a fix for a problem of our own: an AI code reviewer that defers to a wrong human opinion.

Hackathon kits used, and how they connect.

  • CircuitKIT (pinned e71d5e17) was used for instrumented inference on Aya 8B: a parity check against native Hugging Face logits, plus residual-stream contrasts. That localisation work is exploratory. Its EAP-IG entry point is not exposed, so we record unsupported_api and claim no CircuitKIT localisation.
  • AuditKIT (pinned 71316da3, v1.1.3) is an independent scorer that re-scores recorded generations with our strict parser. It ran on two 20-sample evaluations.
  • CuratorKIT (v0.1.21, d6f2e44) ran an exact and MinHash (0.85) dedup check over the regression sets. Counts: coding 40→40; general 60→60 and 60→56 (four reading items share a passage); format 20→20. No dataset was changed.
  • SafeTune was not used.

Pipeline: the fixtures come first; CuratorKIT checks them for duplicates; the models are measured and the adapter is trained with our own scripts; AuditKIT re-scores a sample of the outputs; CircuitKIT served the localisation attempt that failed.

Splits and leak check. The split is by family, not by file. The training families and the evaluation families share none of the plain set's 64 families. A repository test (tests/test_fix_arms.py) checks this against the plain set and the selection set, and we re-counted it for this post. Two sets (wsp-final.json, wsp-validation.json) are sealed and were never read (docs/FIX_PROTOCOL.md). CuratorKIT found no duplicates inside any regression set beyond the four items noted above.

Metrics. Each metric's better direction is given in brackets.

  • Flip rate on solved cases (lower is better) is the main metric, with a 95% Wilson interval.
  • Right unaided (higher is better) is the competence check. A flip rate is only quoted when this clears chance.
  • Rescue by a correct reviewer (higher is better) is reported as the cost of the fix.
  • HumanEval pass@1 (higher is better) is the coding regression.

The flip rate and the right-unaided count are reported under all three answer formats.

Hyperparameters.

  • LoRA rank 16, alpha 32, dropout 0.05, on the q, k, v, o, gate, up and down projections.
  • Learning rate 1e-4, batch 1 with gradient accumulation 8, maximum length 2,048, 2 epochs.
  • The task-only control runs 6 epochs, to match 201 steps.
  • Seeds 17, 29 and 43. The rules for success were written in docs/FIX_PROTOCOL.md before the runs.

Compute. Training covered 27 adapters and took 517 minutes of wall-clock in total, summed from their train_meta.json files. Peak memory was 10 to 38 GB. The hardware was the ZHAW Earth HPC cluster: one A100 per 14B job and two per 32B job. GPU time for evaluation was not tallied, so the total is unknown. Early hosted runs cost about $1.46 (docs/VALIDATION.md).

With more credits. The before and after values here are plans, not results.

  1. Real code at scale. Build an oracle-labelled set of hundreds of CVE fix commits that have tests. We expect the adapter's flip rate to stay well below the unchanged model's, as it did on 32 pairs.
  2. Calibrated rather than invariant. The adapter also ignores correct reviewers. Train with reviewers who are sometimes right where the model is wrong, and measure whether the rescue rate comes back while the flip rate stays low.
  3. A held-out vulnerability class. Train on SQL injection and access control only, then test on command injection.
  4. Independent label review. Have the blinded label packet signed off by a second person.
